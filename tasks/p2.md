# P2 - Weather, planner, and the daily plan

In this task AgroPilot answers the grower's real question:

> Should I water this plot today, and for how many minutes?

You will add two new services, `weather-service` and `planner-service`, and show the plan in the UI.

```text
                                      ┌────────────────────┐
                               ┌────► │  registry-service  │ ──► PostgreSQL (prod) / registry.db (dev)
                               │      │  :8000             │
 ┌─────────┐   ┌────────────┐  │      └────────────────────┘
 │ Browser │ ─►│ Next.js UI │ ─┤      ┌────────────────────┐      ┌────────────────────┐
 └─────────┘   │ :3000      │  └────► │  planner-service   │ ───► │  registry-service  │
               └────────────┘         │  :8002             │      └────────────────────┘
                                      │                    │      ┌────────────────────┐
                                      │                    │ ───► │  weather-service   │ ──► Open-Meteo
                                      └────────────────────┘      │  :8001             │
                                                                  └────────────────────┘
```

Each service is a separate folder under `services/`, with its own `pyproject.toml`, its own `.env`, and its own tests. Services never import each other's code. They talk over HTTP only.

## Part 1 - Registry on PostgreSQL

Complete the exercise **Move the registry to PostgreSQL, with Superpowers skills set** from the [coding agents tutorial](../tutorials/intro_to_coding_assistant.md), if you haven't already. In short:

- The app reads the database URL from `DATABASE_URL`.
- Data access goes through SQLAlchemy.

Install PostgreSQL on your machine ([download](https://www.postgresql.org/download/)), create a database named `registry`, and run the service against it. This is your "production".

The seed script only knows SQLite. Your PostgreSQL database needs the same 15 rows. How the tables and the seed rows get into PostgreSQL is a decision for the brainstorming session. Write it in the service README.

## Part 2 - Configuration in `.env`

Every value that can change between your laptop and production lives in the service's `.env` file, never in the code: database URLs, the URLs of other services, timeouts, retries, cache TTL, API keys.

- Each service reads its settings with [pydantic-settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/), in one `config.py` file.
- Each service has a `.env.example` with every variable and a safe example value. Commit it.
- `.env` is never committed. Check `git status` before every commit.
- Block your coding agent from reading `.env`. In the project root, create `.claude/settings.json`:

    ```json
    { "permissions": { "deny": ["Read(**/.env)"] } }
    ```

    This is not a security boundary, only a guard against accidents. A real production secret never belongs on a machine where an agent runs commands.
- Write `docs/config.md`: every variable, what it does, its default, and which value you use in dev and in production.

A service must start with a clear error when a required variable is missing, not crash later on the first request.


## Part 3 - weather-service

Plans depend on the weather. A hot, dry, windy day pulls more water out of the field. `weather-service` fetches the daily forecast from [Open-Meteo](https://open-meteo.com/en/docs) and serves it to the rest of the system.

Why a separate service just to wrap someone else's API? Think about it while you build it. You will be asked in the review.

### What it does

- It knows coordinates and dates. It knows nothing about farms, plots, or crops.
- For each of the next days it returns two numbers: **ET0** (how much water a standard patch of grass loses to sun and wind that day, in mm) and **rain** (mm).
- Open-Meteo is slow sometimes, and sometimes down. The service keeps its own cache in its own database, with the same `DATABASE_URL` pattern as the registry (`weather.db` locally).
- Two requests for points that are very close to each other (same 0.1° grid cell) share one cache entry. A cache entry is fresh for 3 hours.
- When Open-Meteo fails (timeout, error status, malformed JSON), the service retries, then answers from the last cached forecast with `stale: true`. When there is nothing in the cache, it answers `503`, `code`: `UNAVAILABLE`, with a `Retry-After` header.
- It never answers with made-up numbers. A forecast of zeros looks like "no water needed". That is the worst possible bug in this system.

Open-Meteo's free tier needs no key. Put the provider base URL and an API key variable in `.env` anyway (the key may be empty), so moving to a paid plan, or to another provider, is a config change.

### API

`GET /v1/forecast?lat=31.25&lon=34.79&days=7`

```json
{
  "lat": 31.25,
  "lon": 34.79,
  "source": "open-meteo",
  "fetched_at": "2026-11-12T06:00:00Z",
  "stale": false,
  "days": [
    { "date": "2026-11-12", "et0_mm": 3.1, "rain_mm": 0.0 },
    { "date": "2026-11-13", "et0_mm": 2.8, "rain_mm": 4.2 }
  ]
}
```

`days` holds exactly `days` entries, starting today. Open-Meteo's own field names never leave the adapter that talks to it.

Find in the Open-Meteo docs which daily variables give you ET0 and rain, and what their units are. Write it in the service README.

### Write the requirements yourself

This time the spec is yours. Create `docs/requirements/P2-weather.md` with:

- **Functional requirements** `FR-2.1`, `FR-2.2`, ... One behavior each. Cover the bullets above, the invalid inputs (bad `lat`, `lon`, `days`), and every failure.
- **Non-functional requirements** `NFR-2.1`, ... Each one with a number and a way to measure it. At least: response time on a cache hit, and response time when Open-Meteo is down (the grower must not wait for a dead provider).
- **A user flow** as a [Mermaid](https://mermaid.js.org/syntax/sequenceDiagram.html) sequence diagram: request, cache hit or miss, provider call, retry, fallback, `503`.
- **One decision**: how old can a stale forecast be before you stop serving it? Say why.

A requirement without a number or a pass/fail test is not a requirement.

### Tests never call Open-Meteo

Record a few real Open-Meteo responses into fixture files and commit them. Put the provider behind a small interface (a **port**), with two adapters: the real HTTP client, and a fake one that reads fixtures or raises errors. Tests use the fake.

You'll need fixtures for the bad days too: a timeout, a `500`, a body that isn't JSON, a body with a missing field.


## Part 4 - planner-service

A grower has a plot of tomatoes with drip irrigation. `registry-service` knows the plot. `weather-service` knows the next 7 days. `planner-service` turns those two into a 7-day plan:

> Today: water for 38 minutes. Tomorrow: no need. Day 4: 45 minutes.

Nobody expects you to know agronomy. Part of the task is learning to find, check and document domain knowledge with an AI assistant, the way you would in the first month of a job in an unfamiliar field.

### Five ideas in plain words

- **mm of water.** Water is measured as a depth. 1 mm over 1 m² of ground is 1 litre. All planning is done in mm, and converted to litres at the end.
- **ET0** (from `weather-service`). How much water standard grass loses in one day, in mm.
- **Crop factor (Kc).** Different crops, and the same crop at different ages, drink different amounts. Kc scales the grass number to your crop and its growth stage. A small plant uses much less than a full-grown one.
- **Drip emitters.** Small outlets along a pipe, each releasing a fixed flow in litres per hour. How many emitters the plot has, and how fast each one flows, decides how long the system must run to deliver a given amount of water.
- **The soil bucket.** The idea that turns a daily calculation into a plan. See below.

### The soil bucket

Think of the soil under the plants as a bucket of water.

- The size of the bucket depends on the soil type (sand holds little, clay loam holds a lot) and on how deep the roots reach.
- Rain and irrigation fill it.
- The crop drains it a little every day. Hot days drain it faster.
- The plant is happy while the bucket is more than half full. When the level would fall below the 50% line, it's time to irrigate and refill.

Without a bucket you would water every day. With a bucket you water only when needed, and yesterday's rain still counts today. That's why the engine needs memory between days: the level at the end of one day is the starting level of the next.

An illustration only: a 70 mm bucket, the crop drains 7 mm per day, no rain.

| Day | Start of day (mm) | Crop uses (mm) | End of day (mm) | Decision |
| --- | --- | --- | --- | --- |
| 1 | 70 | 7 | 63 | no irrigation |
| 2 | 63 | 7 | 56 | no irrigation |
| 3 | 56 | 7 | 49 | no irrigation |
| 4 | 49 | 7 | 42 | no irrigation |
| 5 | 42 | 7 | 35 | no irrigation (exactly at the line) |
| 6 | 35 | 7 | would be 28 | irrigate, refill the bucket |

Your job is to find the real numbers for each soil, crop and day, and to decide how to handle what this table hides: rain on a day you were about to irrigate, a bucket that can't overflow, the very first day.

### Find the answers (don't skip this)

The formulas are deliberately not given. Finding them, checking them and writing them down is the exercise.

1. **Ask your AI assistant to research, not to code.** For example:

    > I'm building a daily drip-irrigation planner. Using the FAO-56 method, explain step by step how to go from reference evapotranspiration (ET0) and a crop coefficient to the water a crop needs, how a simple soil-water bucket works, and how to turn mm of water into minutes of drip irrigation. Cite the chapter or table for every claim.

2. **Check the primary sources.** An AI answer without a source is a guess. Open the source and check:
    - [FAO Irrigation and Drainage Paper 56](https://www.fao.org/3/x0490E/x0490e00.htm): crop coefficients, growth stages, and the chapter on soil water availability.
    - The Open-Meteo docs: what exactly its daily ET0 and rain fields mean.
    - Netafim's public data sheet for the DripNet PC emitter: the real flow values.
3. **Write down what you decided.** Create `services/planner-service/docs/engine-spec.md`: every formula, unit, table value and assumption, each with its source. Where sources disagree or leave a gap, make a choice and say why.
4. **Calculate three cases by hand**, on paper or in a spreadsheet, before any engine code exists. They become your first tests.
5. **Only now** let the coding agent implement the engine from your spec. Review what it wrote. A classic AI mistake is silently mixing units (mm, mm per hour, litres). Check every unit yourself.

### A skill that keeps your agent honest

Package what you learned as a knowledge skill, `irrigation-calc-reference`, in `.claude/skills/` (see [Writing Skills](../tutorials/writing_skills.md)): your verified formulas, the tables, the unit conventions, and your hand-calculated cases. Its description tells the agent to load it before it touches the engine.

Without it, the agent re-invents the domain, a bit differently, in every session.

### API

`GET /v1/plots/{id}/plan?days=7`

The planner gets the plot, its soil and its emitter from `registry-service`, and the forecast for the plot's `lat`/`lon` from `weather-service`.

For each day the plan has: `date`, `et0_mm`, `kc`, `need_mm`, `litres`, `run_minutes`, `stale`, plus whatever explains the decision (for example the bucket level). A day with no irrigation has `run_minutes: 0`. The first day is today's recommendation.

Design the exact JSON yourself, and add an example to the service README.

### Rules

- **The engine is pure Python.** No HTTP, no database, no `datetime.now()`. Plain data in, plain data out. The HTTP clients for registry and weather are separate adapters.
- **Domain tables are data files**, not constants buried in code: crop factors and growth stages, root depth.
- **Every number in the plan comes from your engine.** No AI model computes or adjusts irrigation numbers.
- **Calls to other services have a timeout** (in `.env`).
- **Stale weather** still gives a plan, every affected day flagged `stale: true`.
- **Unknown plot**: `404`, `code`: `NOT_FOUND`.
- **registry-service or weather-service down**: a clear degraded response, `problem+json` with `code`: `UPSTREAM_UNAVAILABLE` that says which service failed. Never a `500`, never a crash, and never a plan of zeros.


## Part 5 - Tests and coverage

**What is test coverage?** It's the percentage of your code lines that run when the tests run. A line without a test is a line nobody checks. If it breaks, you won't know.

A test can pass and still miss things. Your tests probably check that `POST /v1/plots` creates a plot. But does any test make the database unreachable, and check that the API answers `503` with `Retry-After` and `UNAVAILABLE`? If not, that code never runs in the tests, and you don't know how it behaves.

Measure it in each service:

```bash
uv add --dev pytest pytest-cov
uv run pytest --cov --cov-report=term-missing
```

The `Missing` column lists the lines no test ran.

The target is **100% line coverage in each of the three services**. If a line truly can't be tested, mark it with `# pragma: no cover` and explain why in the pull request. "The agent couldn't" is not a reason.

- Test through the API (FastAPI's `TestClient`): every endpoint, its success case, and every failure case it can return.
- Tests never need the network or another running service. The planner tests use fakes for registry and weather.
- The engine tests are your three hand-calculated cases, plus the check value below.
- 100% coverage does not mean correct. A test that runs a line without checking the result covers it, and proves nothing. Read the tests the agent wrote.

No UI tests in this task.

## Definition of done

- **Check value.** A 1000 m² tomato plot at mid-season, ET0 = 6.0 mm, no rain, rows 1.5 m apart, emitters every 0.4 m at 1.0 L/h. Replacing one day of crop water use takes about **248 minutes**. If your engine disagrees, find out why before you move on.
- Your three hand-calculated cases pass. The engine matches your own spec on all of them within 0.5%.
- With the three services running, `GET /v1/plots/{id}/plan` returns a 7-day plan for each of the 4 seed plots, and the UI shows today's recommendation for each.
- Stop `weather-service`: the planner returns a degraded response, and the UI says so. Restart it with a 1-minute cache TTL and a wrong Open-Meteo URL in `.env`. After the cache expires, the plan comes back flagged stale.
- `registry-service` runs against PostgreSQL, and its P1 behavior hasn't changed.
- `uv run pytest --cov` shows 100% (or every excluded line is explained) in each service.
- No secret in git. `git log -p | grep -i key` finds nothing you would be embarrassed by.
